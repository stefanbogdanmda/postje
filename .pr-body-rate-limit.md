# Persistent rate limiting (Part A improvement #2)

## Summary

Moves the magic-link rate limiter from an in-process `Map` to a Postgres-backed sliding-window log. The same `5 requests / 15 minutes / per email` policy is preserved, but it now survives restarts and works correctly across Vercel Function instances. The generic per-IP rate limiter used by the photo upload, photo analyze, and post-generation API routes is migrated alongside it.

## Why

The previous limiter in `src/lib/rate-limit.ts` was an in-process `Map<string, number[]>`. Two structural problems on Vercel:

1. **Each Function instance has its own memory.** Fluid Compute reuses instances across concurrent requests, but a second instance spun up under load has an empty Map. Five rapid magic-link requests to two instances bypassed the limit entirely.
2. **Restarts wipe the counter.** A redeploy or cold start reset the limit. An attacker that triggered a redeploy got a fresh budget.

Now every request goes through a single Postgres table — there is one source of truth across all instances and all restarts.

## Approach

- New table `auth_throttle` with one row per attempt (`id`, `key`, `requestedAt`) and a composite index on `(key, requestedAt)`.
- New module `src/lib/auth/throttle.ts` exposes `isMagicLinkRateLimited(email, { db })` and a generic `isKeyRateLimited(key, { maxRequests, windowMs }, { db })`.
- Algorithm: sliding-window log inside a `SERIALIZABLE` transaction:
  1. `DELETE` expired rows for this key (inline cleanup)
  2. `SELECT count(*)` for this key
  3. If at the limit, return `true` (do not insert — matches the in-memory behavior so a hammered key stays at exactly `MAX_REQUESTS` rows)
  4. Otherwise insert and return `false`
- Serialization conflicts retry once; a second conflict fails closed (returns `true` — never under-throttle).
- The old in-memory module is deleted. The `request-rate-limit.ts` wrapper used by three API routes is migrated to call the new async function.

See [docs/superpowers/specs/2026-05-12-rate-limit-persistence-design.md](docs/superpowers/specs/2026-05-12-rate-limit-persistence-design.md) for the full design rationale.

## Test coverage

10 new tests in `src/lib/auth/__tests__/throttle.test.ts`:

- First request returns `false` and inserts a row
- 5 requests pass, the 6th is blocked
- Over-limit attempts do NOT insert (table stays at 5)
- Rows older than the window are treated as expired
- Expired rows for this key are deleted on the next call
- Cleanup does NOT touch other keys
- Case-insensitive: `Foo@Example.com` and `foo@example.com` share a counter
- Generic helper enforces its own `{ maxRequests, windowMs }`
- Distinct generic keys don't share counters
- `deps.now` is optional (falls back to `new Date()`)

Full suite: **125/125 green** (up from 115; the 10 new tests are additive — no existing test changed).

## Manual smoke checklist for the human

After merging and deploying:

- [ ] Confirm migration applied on Neon production: `SELECT * FROM auth_throttle LIMIT 1` returns 0 rows (table exists, empty)
- [ ] Try requesting a magic link 6 times within 15 minutes for `stefanbogdanmda+throttle@gmail.com`. Resend dashboard should show 5 sends, not 6.
- [ ] After ~16 minutes, request again — the 6th attempt should succeed (fresh window).
- [ ] Confirm `SELECT count(*) FROM auth_throttle WHERE key = 'stefanbogdanmda+throttle@gmail.com'` shows ≤ 5 rows.

## Notes / follow-ups

- **The `Db` type alias is now triplicated** across `src/lib/posts/repository.ts`, `src/lib/alerts/check-stale-posts.ts`, `src/lib/alerts/check-regen-limits.ts`, and now `src/lib/auth/throttle.ts`. Should be extracted to `src/db/types.ts` in a follow-up refactor (not part of this branch per the handoff's scope guidance).
- The generic per-IP rate limiter (used by `/api/photos/upload`, `/api/photos/[id]/analyze`, `/api/generate-posts`) now also benefits from cross-instance correctness — previously those endpoints had the same in-memory bypass.
- `auth_throttle` rows are cleaned up inline only when the same key calls in again. Fully abandoned keys (one-off attackers who never come back) leave rows behind. At v1 scale this is fine; revisit if the table grows past ~10k rows.

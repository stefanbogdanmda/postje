# Postgres Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace SQLite (better-sqlite3, local file) with Neon Postgres (Vercel Marketplace, free tier). After this lands, the app can deploy to Vercel and survive function cold starts, multi-instance traffic, and redeploys.

**Architecture:** Drizzle's Postgres dialect (`drizzle-orm/pg-core`) with the Neon serverless driver (`@neondatabase/serverless` Pool). Every repository function converts from synchronous (better-sqlite3 returns rows directly) to asynchronous (pg driver returns promises). Tests run against PGlite — an in-memory single-file Postgres — so unit tests stay fast and don't need Docker. Auth.js's `DrizzleAdapter` is dialect-agnostic and works as-is once the schema swaps.

**Tech Stack:** TypeScript, Next.js 16 App Router, Drizzle ORM, `@neondatabase/serverless`, `@electric-sql/pglite` (for tests), Vitest, Resend, Vercel Cron.

**Sequencing doc:** `docs/superpowers/specs/2026-05-11-part-a-improvements-sequencing.md`

**Branch:** `feat/postgres-migration` (already exists; sequencing doc + this plan are the only commits so far)

**Prerequisites:**
- Stefan has access to the Vercel dashboard for this project.
- The `main` branch up to commit `2c8ed3a` (regen-limit-alerts merged) is in this branch's history.

## What this plan does NOT do

- Does NOT migrate production data — there is none yet.
- Does NOT change product behaviour — every existing test must still pass.
- Does NOT add a new index, new column, or new feature. Schema column NAMES stay identical; only column TYPES adapt to the Postgres dialect.
- Does NOT deploy to production. The final task does a Vercel preview deploy; promotion to production is a separate decision and a separate plan.

## Decisions locked in (with rationale)

**Driver: `@neondatabase/serverless` + `drizzle-orm/neon-serverless`.**
Picked over `drizzle-orm/neon-http` because the HTTP driver doesn't support transactions, and we use `db.transaction()` in `insertPosts` and `replacePostsForOpenDays`. The serverless Pool driver supports both transactions and Vercel Functions.

**Test DB: PGlite (`@electric-sql/pglite`) via `drizzle-orm/pglite`.**
PGlite is a single-file in-memory Postgres. Tests stay fast (no Docker, no real network), and they run the same dialect as production. The alternative — keeping SQLite for tests — would mean two schema files, which defeats the migration.

**Timestamps: `timestamp({ mode: "date" })`, not `timestamptz`.**
Drizzle's `timestamp` maps to Postgres `timestamp without time zone`. With `mode: "date"` Drizzle returns JS `Date` objects, matching the current better-sqlite3 behaviour. All our timestamps are server-set with `new Date()`, so they're stored as UTC. No app behaviour change.

**JSON columns: `jsonb()`.**
Current schema uses `text({ mode: "json" })` for `photos.analysis`. Postgres's `jsonb` is the right replacement — typed, queryable, indexable.

**Booleans: `boolean()`.**
Current schema uses `integer({ mode: "boolean" })` for `users.hasLoggedIn`. Postgres has a native `boolean`. The DrizzleAdapter does not require boolean columns — this is project state.

**Enum columns: keep as `text` with TypeScript enum types.**
The schema uses `text("status", { enum: [...] })` for `posts.status`, etc. Postgres has `pgEnum`, but introducing it requires extra migration ceremony (CREATE TYPE statements). For greenfield with no production data, plain `text` columns with TS-side enum constraints are simpler and behave identically.

**IDs: stay as `text` UUIDs.**
The schema uses `text("id").$defaultFn(() => crypto.randomUUID())` everywhere. Postgres has `uuid` and `gen_random_uuid()` but switching dialect AND ID type AND value generator at once is too many variables. Keep text+`crypto.randomUUID()` for this migration.

**Sync → async: full conversion in one plan, not behind a compatibility shim.**
better-sqlite3 is sync; pg is async. There is no clean middle ground. Every call site changes. This is mechanical work but it's the bulk of the diff.

# GDPR data export + account deletion (Part A improvement #4)

## Summary

Gives clients self-service GDPR rights: a one-click data export and a delete-account flow with a 24-hour cooling-off window. The admin "delete user" endpoint is refactored to share the same core deletion logic, so it now also cleans up Vercel Blob files (previously orphaned them).

## Why

[CLAUDE.md](CLAUDE.md) §11 calls GDPR compliance a launch blocker. Before this branch, there was no client-facing path to export data or delete an account — only Stefan-as-admin could delete via [src/app/api/admin/delete-user/route.ts](src/app/api/admin/delete-user/route.ts), and even that left photo blobs behind in Vercel storage.

## Approach

**Export.** Server Action gathers everything scoped by `clientId` (user + client + photos + posts + active deletion request status), returns a JSON string. A client component creates a Blob URL and triggers a download. Schema is versioned (`schemaVersion: 1`) so the format can evolve.

**Delete request.** New `deletion_requests` table tracks the request. When the user clicks "Delete":
1. Row inserted with `scheduledFor = requestedAt + 24h` and a random `cancelToken`.
2. Email sent via Resend with a "Annuleer verwijdering" link containing the token.
3. Banner shows on `/dashboard` and `/dashboard/account` until cancelled or completed.
4. New hourly cron `/api/cron/process-deletions` finds due rows and runs the deletion.
5. Deletion: writes audit log → best-effort blob cleanup → DB delete (FK cascade does the rest).

**Cancel.** Either via the email link (public GET `/api/account/deletion/cancel?token=...`) or the in-app "Annuleren" button (Server Action). The email link never reveals whether a token was valid (information-leak prevention).

**Admin refactor.** `/api/admin/delete-user` now calls the shared `deleteUserAccount` function, so admin deletions also delete blobs. The admin-only safety checks (auth, role check, "cannot delete admins") remain in the route handler.

See [docs/superpowers/specs/2026-05-12-gdpr-export-deletion-design.md](docs/superpowers/specs/2026-05-12-gdpr-export-deletion-design.md) for the full design, including all decisions documented in §2.

## Manual smoke checklist for the human

After merging and deploying:

- [ ] `SELECT * FROM deletion_requests LIMIT 1` — table exists, empty
- [ ] Sign in as a test client. Upload a photo. Generate posts. Approve one.
- [ ] Go to `/dashboard/account`. Click "Download mijn gegevens". Confirm: JSON downloads with `schemaVersion: 1` and all your data, no auth tokens.
- [ ] Click "Account verwijderen" → confirm in dialog. Banner appears. Email arrives.
- [ ] Click "Annuleer verwijdering" in the email — lands on `/account/deletion/cancelled`. Banner disappears from dashboard.
- [ ] Re-request deletion. SQL-update `scheduledFor` to the past. Trigger `/api/cron/process-deletions` with the CRON_SECRET. Confirm: user, client, photos, posts deleted; `deletion_audit_log` row exists; Vercel Blob files removed.

## ⚠️ Migration-number conflict with `feat/rate-limit-persistence`

Both this branch and `feat/rate-limit-persistence` add a migration numbered `0001_*.sql` because they're both based on `feat/postgres-migration`. When merging:

1. Merge `feat/rate-limit-persistence` first → main now contains `0001_sharp_wolfpack.sql`.
2. Rebase this branch onto the updated main.
3. Rename `src/db/migrations/0001_early_alex_power.sql` → `0002_*.sql`.
4. Update `src/db/migrations/meta/_journal.json` to renumber the entry from idx `1` → `2`.
5. Rename `meta/0001_snapshot.json` → `meta/0002_snapshot.json` and update its contents. (Easiest: delete the snapshot and re-run `npm run db:generate` after the rebase — it will regenerate the snapshot at the right number.)
6. Push the rebased branch and merge.

Note: on the dev Neon DB, both migrations have already been applied (each one is additive — `auth_throttle` and `deletion_requests` are unrelated tables). Production starts clean and applies whichever order Drizzle processes after the renumber.

- Email re-confirmation step before scheduling
- 30-day backup retention after `completedAt`
- Admin-side UI showing pending deletion requests (subsumed by Part A #3 Attention List)
- Two-factor on the delete action
